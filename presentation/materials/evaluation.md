# Lightweight testing and evaluation plan

Updated after the user's request on 2026-11-07: keep evaluation and test cases simple and reduce per-case overhead. This plan supersedes the earlier 12-case pilot and 30/20 split. No new model outputs were generated by writing this plan.

## Test cases

Prepare 50 short, fictional inputs using the existing input structure. Allocate 8 greeting, 9 recommendation, 8 aftercare, 8 reactivation, 8 invitation and 9 price-objection cases. Vary the product, expressed need, relationship and amount of information without adding unnecessary backstories. Include ordinary missing-information and customer-concern cases. Test explicit no-contact cases separately so each of the 50 submitted cases has three outputs.

Start with one case per scenario (6 total, including the existing recommendation case). Review their results together and make one consolidated prompt revision if needed. Then run the other 44. If the prompt changes, re-run the initial six with the final version before assembling the final 50-case output table. Preserve all original versions and actual defects. The first six are used for development; do not call the final 50 an untouched independent test set.

## Simple review

Review each group of three messages once. Use four columns, each marked pass or issue:

| Check | Pass means |
| --- | --- |
| Facts and boundaries | No invented or contradictory consequential details, unauthorized promises or conflict with explicit contact restrictions. |
| Scenario and context | All three respond to the actual task and the client's latest statement. |
| Chinese expression | Warm, concise, readable Chinese with natural short sentences; no stiff or pushy wording. |
| Three useful choices | Exactly three candidates that offer useful differences without changing the facts. |

Overall label: **Pass** when all checks pass; **Needs edit** for minor expression or variation issues; **Fail** for unsupported claims, explicit-boundary violations, wrong task or missing outputs. A provider error is a technical failure, not a passing case. Record one short reason only when an issue is found, pointing to the affected output number. Example: “Output 2: promises a discount not supplied in the input.” No long case-by-case essays or numerical scoring.

This is a lightweight assisted review, not independent advisor validation. Record the actual reviewer and do not claim customer/business impact. Mechanical checks verify shape and count only; factual and language review still require reading the outputs.

## Deliverables

- One 50-row input/output table using the brief's required columns, plus prompt version.
- One short evaluation table: case ID, four checks, overall label, issue note and reviewer.
- A brief summary with label counts, common defects and a few representative examples.
- Actual before/after examples for revisions that were made; preserve raw outputs.
- Work-log entries per batch/activity, with real screenshots where available, rather than one work-log entry per case.
